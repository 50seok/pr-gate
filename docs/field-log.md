# field-log — pr-gate 실사용 판정 기록

CareerRAG(1인 프로젝트, `50seok/CareerRAG`)에 관찰 모드로 붙여서 얻은 실측 데이터.
목적은 CareerRAG 코드 품질이 아니라 **pr-gate 판정 자체가 맞는지**다.

형식: `PR #N  머신 판정 → 정탐/오탐/누락. 근거`

---

PR #1  머신: 라벨 없음(문서만 있는 PR, P1/P2/P3 없음) → 정탐. docs만 바꾼 PR이라 지적할 게 없었다.

PR #2  로더 6종 + Chroma 인덱스 3개 + 3단계 폴백 검색. 3라운드.
- R1: P1 0 · P2 3 → 3건 다 정탐 (id 충돌로 인한 조용한 덮어쓰기 / frontmatter 없는 파일에서 전체 재색인이 죽는 IndexError / 개인 경로가 박힌 sources.toml 커밋)
- R2: P1 0 · P2 3 → 3건 다 정탐. R1에서 고친 id 충돌 패턴이 load_resume엔 안 옮겨진 것, prepdocs 로더의 html/md id 충돌, index.py 빈 파티션 upsert 크래시
- R3: P1 0 · P2 0 · P3 1 → 수렴
- 누적: **6/6 정탐, 오탐 0**

PR #4  금지 주장 목록 + 생성 파이프라인 + 검증 3종(verify.py). 3라운드.
- R1: P1 0 · P2 2 · P3 1 → 3건 다 정탐.
  - search_reviews의 dedupe 기본값 변경이 eval_retrieval.py 등 기존 호출부를 조용히 다른 동작으로 바꿈
  - verify.annotate()가 check()의 정규화된 문장을 원문에서 곧이곧대로 찾아, 개행/태그가 섞이면 마킹이 조용히 빠짐 (annotate 자체 버그의 연장선 — 같은 세션에서 내가 고친 부분의 잔여 결함을 머신이 다시 잡음)
  - generate.py save()가 --회사 인자를 경로에 그대로 써서 '/'·'..' 새니타이즈 없음
- R2: P1 0 · P2 1 · P3 1 → 2건 다 정탐, 그중 하나가 제일 심각했다.
  - **_normalize_with_map()이 짝 없는 '<'(예: "지연시간 < 100ms")를 태그 시작으로 오인해 그 뒤 원문 전체를 공백 하나로 뭉갬 → 문서 뒷부분 전체가 금지주장·유령인용·무근거주장 검사에서 조용히 빠짐.** R1에서 내가 새로 짠 코드가 R2에서 바로 다음 결함을 냈는데 머신이 그걸 잡았다 — 자기 코드를 자기가 리뷰 못 하는 문제를 그대로 보여주는 사례
  - count_by_interview() 죽은 코드
- R3: P1 0 · P2 0 · P3 1(미사용 import) → 수렴, 머지
- 누적: **6/6 정탐, 오탐 0**

2026-09-11  절차 이탈 — PR을 안 거치고 `dev`에 직접 커밋 (FC-004 'PR' 탐지어가
"Spring"의 "pr"에 오탐하던 버그 수정). 그린텍 재생성 실사용 중 발견해서
바로 고쳤는데, 문서 갱신("머지 직후" 패턴)과 실제 로직 수정을 같은 취급해서
`feature/*` → PR → pr-gate 검수 단계를 건너뛰었다. **이 수정은 pr-gate가
못 본 코드다** — field-log의 "정탐/오탐" 집계에 안 잡히는 사각지대라는
뜻이라 남겨둔다. 테스트 42개 통과 + 실제 재생성 2회로 사람이 직접 검증은
했지만, 머신 리뷰라는 관찰 대상 자체가 빠진 케이스.
