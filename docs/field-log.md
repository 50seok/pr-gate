# field-log — pr-gate 실사용 판정 기록

CareerRAG(1인 프로젝트, `50seok/CareerRAG`)에 관찰 모드로 붙여서 얻은 실측 데이터.
목적은 CareerRAG 코드 품질이 아니라 **pr-gate 판정 자체가 맞는지**다.

형식: `PR #N  머신 판정 → 정탐/오탐/누락. 근거`

  - count_by_interview() 죽은 코드

뜻이라 남겨둔다. 테스트 42개 통과 + 실제 재생성 2회로 사람이 직접 검증은
했지만, 머신 리뷰라는 관찰 대상 자체가 빠진 케이스.

PR #15  FastAPI + 브라우저 UI (Phase 6, 화면 4개). pr-gate 앞에 내(메인 세션) 자체
code-reviewer 서브에이전트 1라운드(P1 XSS raw-HTML·P2 500크래시·Low 시그니처, 픽스 후
재검토에서 `<br>` 표시 회귀까지 잡아 수정)를 먼저 거친 뒤 PR을 열었다. pr-gate는
그 이후 상태(커밋 `b89c971`)부터 관찰.
- R1: P1 1 · P2 1 → **둘 다 정탐, 이 프로젝트 최초의 P1.** P1은 앞선 내 자체 리뷰가
  이미 한 번 고친 `render_result_html()`(html.escape 선처리)이 raw HTML은 막았지만
  **마크다운 링크 문법**(`[클릭](javascript:...)`)이 `markdown()` 변환 중 만들어내는
  `<a href="javascript:...">`는 못 막는 우회 경로 — python-markdown이 링크 URL 스킴을
  검증하지 않아 실제로 재현됨. P2는 `check_invented()`/`_sections_to_text()`가
  `items`(리스트 기대)에 문자열이 오면 `or []`로 안 걸러져 문자 단위로 순회 —
  무결성 검사가 사실상 무력화되는 조용한 데이터 오염이었다. **내 자체 code-reviewer도,
  그 재검토 라운드도 둘 다 놓친 결함을 pr-gate가 잡았다** — PR #4·#8 R2와 같은 계열의
  "직전 수정이 새 결함을 남기고, 다음 라운드가 그걸 잡는" 패턴이지만 이번엔 자체
  리뷰 다음 단계인 pr-gate에서 처음 나타났다.
- R2: P1 0 · P2 0 · P3 0 → 수렴. P1 픽스는 정규식 화이트리스트를 반복 확장하는 대신
  `nh3`(허용목록 새니타이저) 도입으로 우회 경로 자체를 원천 차단하는 방향으로 바꿈.
- 누적: **2/2 정탐, 오탐 0.**

  다르다 — 사람(메인 세션)이 직접 지시한 리뷰·재검토 두 단계를 거치고도 남은 결함을
  pr-gate가 세 번째 방어선에서 잡았다. 자기 코드(와 자기 리뷰)를 자기가 검증하는
  사각지대는 리뷰 라운드를 늘려도 구조적으로 남는다는 신호로 읽힌다
