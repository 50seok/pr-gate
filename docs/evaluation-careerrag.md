# pr-gate 평가 — CareerRAG 실사용 결과 (2026-09-08 ~ 2026-09-22)

> `docs/field-log.md`의 누적 데이터(PR #1~#32, 10개 PR·28개 리뷰 라운드)를 근거로 한
> **pr-gate 자체**에 대한 평가다. CareerRAG 코드 품질 얘기가 아니라 "머신 판정을 믿어도
> 되는가"가 목적이라는 건 CLAUDE.md에 처음부터 적어둔 전제 그대로다.

**판정 정확도는 기대 이상, 자동 머지는 이 레포에서 한 번도 안 됐다.** 후자는 pr-gate
코드 문제가 아니라 무료 프라이빗 레포의 플랫폼 제약이라, PRD 성공 기준 하나가 애초에
이 환경에서는 검증 불가능했다는 뜻이다. **(2026-09-24 정정: 같은 기능이 public
레포에서는 실제로 작동한 기록이 있다 — §3-1 머리말.)**

## 2. 잘 작동한 것

### 2-1. 자기 자신도 못 잡는 결함을 반복적으로 잡았다

가장 값진 패턴이 **다섯 번** 나왔다 — 직전 라운드(또는 내 자체 code-reviewer)의 수정이
새 결함을 남기고, pr-gate가 바로 다음 라운드에서 그걸 잡는 구조:

| 사례 | 무엇을 놓쳤나 | 누가 고친 코드였나 |
|---|---|---|
| PR #4 R2 | `<` 부등호를 태그로 오인해 문서 뒷부분 전체가 검증 대상에서 빠짐 | 내가 R1에서 새로 짠 검증 코드 |
| PR #8 R2 | upsert 도입이 exclude_type을 조용히 리셋 | 내가 R1 픽스로 넣은 코드 |
| PR #15 R1 | 마크다운 링크 스킴(`javascript:`)이 XSS 방어를 우회 | 내 자체 code-reviewer 리뷰+재검토 **둘 다** 통과한 코드 |
| PR #27 R1 | 전체 팔레트 설계 중 남은 미사용 CSS 변수 | 내 자체 code-reviewer가 같은 라운드에서 다른 죽은 코드는 잡았는데 이건 놓침 |
| PR #32 R1 | 0/1-헤더 엣지케이스에서 카드 스타일 소실 | 내 자체 code-reviewer가 APPROVE한 코드 |

PR #15·#27·#32는 특히 중요하다 — **사람(나)이 직접 지시한 별도 리뷰어(code-reviewer
서브에이전트)를 먼저 거치고 나온 코드에서도 pr-gate가 새로 뭔가를 잡았다.** "자기 코드를
자기가 검증 못 한다"는 게 리뷰 라운드를 늘려도 구조적으로 남는 사각지대라는 뜻이고,
**독립된 리뷰어라는 존재 자체가 리뷰 프롬프트 품질과 별개로 가치가 있다**는 걸 보여준다.

### 2-2. 티어 라우팅이 실제로 규모·위험에 비례했다

PR #6(체크박스+테스트 1개, 진짜 사소한 변경)은 `small`(haiku)로 자동 라우팅됐고 실제로
문제없다고 정확히 판정했다. PR #12(인증·DB)는 `ai:needs-human`으로 라벨이 붙어 클린패스여도
체크가 계속 fail로 남아 사람이 직접 확인하게 만들었다 — **설계 의도(민감 영역은 자동
통과시키지 않는다)가 그대로 동작함을 확인.**

### 2-3. 순수 CSS/문서성 변경에서도 진짜 결함을 잡았다

"로직이 없으니 리뷰할 것도 없다"가 아니었다 — PR #27(CSS 리스킨)·PR #32(HTML 구조 변경)
둘 다 논리적 결함이 아니라 **엣지 케이스 누락**(미사용 변수, 0/1-헤더 케이스)을 잡았다.
정적 분석 툴이 못 잡는 종류의 "이 변경이 의도한 대로 렌더링되는가" 판단을 실제로 했다.

## 3. 구조적 한계 / 놓친 것

### 3-1. PRD 성공 기준 "P1 없는 PR은 사람 손 없이 dev에 머지된다" — 이 환경에서는 한 번도 실현 안 됨

> **2026-09-24 정정 — 범위를 한정해야 한다.** 아래 분석은 **CareerRAG 안에서는 전부
> 맞지만**, "pr-gate 설계의 절반이 미검증"이라는 결론으로 일반화한 건 틀렸다.
> **public 레포(`50seok/pokedex-rag`)에서는 2026-09-04에 실제로 작동했다** — PR #10에서
> auto-merge 예약 `06:18:01` → 머지 완료 `06:18:20`, 19초 차이고 그 사이 수동 머지
> 명령은 없었다. 해당 레포에는 지금도 `allow_auto_merge: true` + `dev` 브랜치 보호의
> required check `["review"]`가 살아 있다.
>
> 즉 **집행 메커니즘 자체는 검증됐다.** 검증 불가능했던 건 pr-gate의 설계가 아니라
> **"무료 프라이빗 레포"라는 이 배포 환경**이다. 아래 내용은 그 환경 제약의 기록으로
> 읽어야 한다.

`docs/PRD.md` §성공기준의 세 번째 항목이자 설계의 핵심(자동 머지)인데, **field-log에
기록된 모든 PR이 예외 없이 사람이 직접 "머지 진행"을 지시한 뒤 `gh pr merge`로
수동 머지됐다.** GitHub 네이티브 auto-merge가 실제로 동작하는 걸 관찰 로그 어디에서도
확인 못 했다.

원인은 pr-gate 코드가 아니라 **배포 환경 자체**다 — CareerRAG의 CLAUDE.md에 이미
적혀 있다: "무료 프라이빗 레포라 브랜치 보호가 안 걸린다... 머지 버튼이 물리적으로
막히지 않으므로 규칙으로 대신 건다." auto-merge는 `dev` 브랜치 보호 규칙에 이 check를
`required`로 등록해야 작동하는데(PRD §범위(In) "사전 설정 1회"), **브랜치 보호 자체가
무료 프라이빗 레포 티어에서 지원되지 않는다.** 즉:

- pr-gate는 P1=0/P1≥1 판정과 라벨을 정확히 붙였다(check 통과/실패는 설계대로 동작)
- 하지만 그 check를 "머지 전 필수"로 강제할 GitHub 측 장치가 애초에 켜질 수 없었다
- 그래서 "머지 차단"도 "자동 머지"도 **전부 사람(또는 Claude 세션)의 규율에 의존**했다
  — "check가 빨간 X면 머지 안 한다"는 CareerRAG CLAUDE.md의 문장 자체가 이 공백을
  메우려고 나중에 추가된 규칙이다

**이건 이번 관찰에서 나온 가장 중요한 발견이다.** pr-gate 판정 품질은 검증됐지만,
**판정을 실제 머지 게이트로 강제하는 절반은 이 환경에서 통째로 검증 불가능했다.**
Private repo를 Pro/Team 유료 티어로 올리거나, 아니면 PRD 자체에 "무료 프라이빗
레포에서는 자동 머지가 구조적으로 불가능하다"는 제약을 명시하고 대안(예: required
대신 이 리포처럼 사람이 라벨을 보고 수동 머지)을 공식 경로로 인정해야 한다.

> **2026-09-24 보강.** 위 문단의 "자동화의 존재 이유"라는 표현은 지웠다 — pokedex-rag
> 사례(§3-1 머리말)가 그 절반이 실제로 도는 걸 보여줬기 때문이다. 정확한 서술은
> **"이 환경에서 검증 불가능"**이지 **"미검증 기능"**이 아니다.

### 3-2. PR을 거치지 않은 커밋은 관찰 범위 밖이다

2026-09-11에 문서 갱신 김에 실제 로직 수정(FC-004 정규식 오탐 수정)을 `dev`에 직접
커밋한 적이 한 번 있다 — pr-gate가 볼 기회 자체가 없었다. "정탐 30/오탐 0"이 인상적인
숫자지만, **이건 "PR로 들어온 것 중"이라는 전제가 붙는다.** 브랜치 보호가 없으니(3-1과
같은 원인) 이걸 기술적으로 막을 방법도 없고, 사람의 습관에 의존한다.

### 3-3. 오탐 0건은 통계적으로 과신하면 안 된다

field-log 자체는 0오탐이라고 적혀 있지만, **이 세션 초반(field-log에 기록되지 않은
시점)에 실제로 haiku 티어 리뷰가 `tests/test_app.py`의 `saramin_sync_mod` 임포트를
"정의 안 된 이름"이라고 잘못 지적한 적이 있다** — 직접 코드를 열어 해당 테스트 4개가
전부 통과하고 있고 프로젝트의 `_mod` 접미사 관례를 그대로 따른 정상 임포트임을 확인해
반박했다. 이건 **진짜 오탐**인데 `field-log.md`에 별도 줄로 기록되지 않았다(어느 PR
라운드였는지도 지금 시점에 정확히 특정이 안 된다).

**반대 방향 편향도 있다(2026-09-24 추가).** 위 문단은 "내가 반박한 오탐이 기록에서
빠진다"는 누락을 말하는데, 그보다 조용한 편향이 하나 더 있다 — **pr-gate가 "고쳐서
나쁠 건 없는" 지적을 하면 사람은 대개 반박하지 않고 그냥 고치고, 그건 정탐으로
집계된다.** 반박이라는 행위가 있어야만 오탐으로 분류되는 구조라, "굳이 안 고쳐도
됐지만 고친 것"은 영원히 정탐 칸에 남는다. PR #27 R2("정탐이지만 의도적으로 안 고침")가
이 경계를 정직하게 기록한 유일한 사례인데, 역방향은 데이터가 아예 없다. 정탐 30 중
몇 건이 여기 해당하는지는 지금 기록으로 알 수 없다.

즉 **"정탐 30/오탐 0"은 field-log에 사람이 수기로 남긴 것의 집계이지, 실제로 발생한
모든 판정의 집계가 아니다.** 작은 haiku 티어 판정 중 "반박하고 넘어간" 것들이 기록
누락될 유인이 있다 — P1/P2로 이어지는 "진짜 사건"은 기록하지만, 금방 반박되고 끝나는
haiku 오탐은 field-log 항목을 새로 만들 만큼 무겁게 안 느껴진다. **표본이 1인·10개
PR·단일 코드베이스(Python/FastAPI, 한/영 혼용)라는 것도 일반화의 한계다.**

## 4. 개선 제안

1. **PRD의 자동 머지 성공 기준을 "무료 프라이빗 레포" 전제와 분리한다.**
   ~~그 전까지는 "설계상 가능하나 미검증"으로 문서에 명시하는 게 정직하다.~~
   **(2026-09-24 갱신) 이 제안이 요구한 관찰은 이미 존재했다** — public 레포
   `50seok/pokedex-rag` PR #10(2026-09-04)에서 auto-merge가 실제로 돌았다(§3-1 머리말).
   따라서 PRD에는 "미검증"이 아니라 **"public 또는 유료 티어에서 검증됨 / 무료
   프라이빗 레포에서는 구조적으로 불가"**로 적는 게 맞다. → PRD 반영 완료.
2. **오탐도 그 자리에서 field-log에 한 줄 남기는 습관을 만든다.** 지금 규칙(`CLAUDE.md`
   "클린패스는 생략, 정탐/오탐/누락일 때만 기록")은 정탐 기준으로는 합리적이지만,
   반박하고 넘어간 haiku 오탐처럼 **"내가 그 자리에서 대응했기 때문에 기록 안 남기고
   싶어지는" 바로 그 케이스가 정작 가장 중요한 데이터다.** 티어별 오탐률을 따로
   보고 싶다면 이게 빠지면 안 된다.
3. ~~**브랜치 보호 없이도 "머지 게이트"를 흉내 낼 최소 장치**— P1이면 PR을 자동으로
   `Draft`로 되돌린다.~~ **(2026-09-24) 기각 — 같은 벽에 막힌다.**

   Draft는 브랜치 보호와 달리 GitHub이 머지 버튼을 실제로 비활성화하므로 아이디어
   자체는 맞았다. 그런데 `gh pr ready --help`가 이렇게 적고 있다:

   > *If supported by your plan, convert to draft with `--undo`*

   **Draft PR도 무료 프라이빗 레포에서는 지원되지 않는다** — 3-1과 정확히 같은 제약이다.
   무료 private에서 물리적 강제력을 만드는 경로는 확인된 범위에서 없다(`gh pr close`로
   PR을 닫는 방법이 남지만 과하고 재오픈 비용이 크다). 즉 **이 티어에서 강제력은
   구조적으로 불가능**이고, 남는 선택지는 public 전환 또는 Pro($4/월)뿐이다.
4. **"직전 라운드가 새 결함을 남긴다" 패턴(5회 관찰)을 리뷰 프롬프트에 명시적으로
   넣는 걸 고려한다** — "방금 고친 부분이 새 버그를 만들지 않았는지 특히 주의해서
   보라"는 지시를 프롬프트에 박아두면, 지금도 잘 잡고 있는 이 패턴을 더 빨리(라운드
   수를 줄여서) 잡을 수도 있다. 단, 이미 잘 작동하는 걸 건드리는 거라 실익이
   크지 않을 수도 있어 우선순위는 낮게 본다.

## 5. 결론

10개 PR·28라운드·30건의 실제 지적 중 반박 가능한 오탐이 field-log 기준 0건이라는 건
개인 프로젝트 리뷰봇치고 상당히 인상적인 성적이다. 특히 **"이미 사람이 리뷰한 코드에서도
새로운 진짜 결함을 찾아낸다"**는 걸 다섯 번이나 반복 확인한 게 가장 큰 소득이다 — 이게
이 프로젝트를 시작한 이유(대조군이 깨끗한 1인 레포에서 머신 판정을 검증) 그 자체였고,
답은 "예, 신뢰할 만하다"로 나왔다.

다만 **"자동 머지"라는 설계의 절반은 이번 배포 환경(무료 프라이빗 레포)에서 단 한 번도
